# ladder-gen — 生成AIによるラダー/ST 自動生成スキル

自然言語の制御仕様を、検証可能な中間成果物を経由して PLC プログラム（ST / ラダー）へ
落とし込むためのスキル。各工程に「ゲート（検証点）」を置き、AI のハルシネーションを
早期に潰しながら、人間レビュー・GX Works3 実装に渡せる形を作る。

## 対象範囲

このスキルが**自動化する**のは次の工程:

```
① 自然言語仕様          （入力。ユーザーから受け取る）
② 構造化仕様の生成      ← このスキル
③ デバイス/ラベル割付   ← このスキル
④ ST 生成               ← このスキル（ST を正とし、ラダーは変換ビュー）
⑤ 静的チェック          ← このスキル（scripts/static_check.py）
─────────────────────────────────
⑥ 人間レビュー          （人間。このスキルはレビュー観点を提示する）
⑦ GX Works3 実装        （人間/外部連携。インポート用ファイルを出力する）
⑧ シミュレーション      （人間）
⑨ 実機確認              （人間）
```

ST を生成の「正」とする。ラダー図は ST からの変換結果（人間が見るためのビュー）と
位置づける。これにより後段の検証・差分管理（Git）を一本化する。

## 成果物の置き場所

各工程の成果物はワークスペース直下の `out/<案件名>/` に出力する:

```
out/<案件名>/
  01_structured_spec.yaml   ← 工程② 構造化仕様
  02_device_master.csv      ← 工程③ デバイス/ラベル割付表
  03_program.st             ← 工程④ ST ソース
  04_static_check.txt       ← 工程⑤ 静的チェック結果
  05_review_notes.md        ← 工程⑥ 人間レビュー用の観点メモ
```

## 実行手順

ユーザーから制御仕様（自然言語）を受け取ったら、以下を順に実行する。
**各工程の終わりにゲートがある。** ゲートを通らない限り次工程へ進まない。

### 工程② 構造化仕様の生成

1. `references/structured-spec-schema.md` を読み、スキーマを把握する。
2. ユーザーの自然言語仕様を `templates/structured-spec.template.yaml` の形式へ構造化する。
   - I/O リスト（入力/出力）、内部リレー・タイマ・カウンタ、状態と状態遷移、
     インターロック、安全要件（非常停止など）を**漏れなく**抽出する。
   - 仕様に明示されていないが制御上必要な項目（非常停止、初期化、相互排他など）は
     `assumptions`（前提）として明示し、勝手に断定しない。
3. `out/<案件名>/01_structured_spec.yaml` に書き出す。
4. **ゲート②**: 抽出した I/O・状態・インターロック・前提を箇条書きでユーザーに提示し、
   不足や誤りがないか確認する。曖昧な点は `AskUserQuestion` で確認する。

### 工程③ デバイス/ラベル割付

1. `references/device-allocation.md` を読む。
2. 既存のデバイスマスタ（アドレス表）があればユーザーから受け取り、入力として使う。
   なければ `templates/device-master.template.csv` を基に新規作成する。
3. **AI は物理アドレス（X0/Y10/D100…）を勝手に確定しない。** ラベル（シンボル名）で
   生成し、物理アドレス列はマスタに従う。マスタが無い項目は採番案を提示して確認する。
4. `out/<案件名>/02_device_master.csv` に書き出す。
5. **ゲート③**: 割付表をユーザーに提示し、実機/既存資産とのアドレス衝突がないか確認する。

### 工程④ ST 生成

1. `references/st-generation-guide.md` を読み、コーディング規約・禁止事項を把握する。
2. 構造化仕様（②）とデバイスマスタ（③）を入力に ST を生成する。
   - ラベル名はデバイスマスタの `label` 列に一致させる（未定義ラベルを作らない）。
   - 二重コイル（同一出力への複数代入）を作らない。
   - 非常停止・インターロックを最上位条件として組み込む。
3. `out/<案件名>/03_program.st` に書き出す。

### 工程⑤ 静的チェック

1. `scripts/static_check.py` を実行する:
   ```bash
   python3 .claude/skills/ladder-gen/scripts/static_check.py \
     --st out/<案件名>/03_program.st \
     --devices out/<案件名>/02_device_master.csv \
     --spec out/<案件名>/01_structured_spec.yaml \
     --report out/<案件名>/04_static_check.txt
   ```
2. `references/static-check-rules.md` でチェック項目の意味を確認する。
3. **�ート⑤（矯正ループ）**: エラーがあれば原因に応じて工程②/③/④へ戻して修正し、
   静的チェックがパスするまで繰り返す。`ERROR` が 0 になるまで次へ進まない。

### 工程⑥ 人間レビュー用メモの生成

静的チェックを通過したら、人間レビュー用に `out/<案件名>/05_review_notes.md` を生成する。
`references/static-check-rules.md` のレビュー観点（安全・スキャン依存・自己保持の妥当性等）
に沿って、レビュアーが確認すべきポイントと、AI が置いた前提（assumptions）を列挙する。

### 工程⑦ GX Works3 への橋渡し

`out/<案件名>/03_program.st` は GX Works3 の ST エディタへインポート/貼り付けする前提の
プレーンな構造化テキスト。GX Works3 側の自動インポート可否はプロジェクト環境に依存するため、
ユーザーに連携方法（CSV/プロジェクト連携/手動貼り付け）を確認する。

## 重要な原則

- **AI に物理アドレスを断定させない。** デバイスマスタを正とする。
- **ST を正、ラダーは従。** 二重生成・二重検証を避ける。
- **安全要件（非常停止・インターロック）は必須ゲート。** 静的チェックで欠落を検出する。
- **不明点は断定せず assumptions に記録し、ゲートで人間に確認する。**
- 静的チェックの `ERROR` が残ったまま工程⑥以降へ進まない。
